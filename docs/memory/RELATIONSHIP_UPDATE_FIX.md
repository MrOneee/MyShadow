# 好感度更新链路修复

日期：2026-11-06。保留当前模型判断规则、分值、半小时去重和每日上限，不通过修改成员分数解决链路问题。

## 问题与证据

原回复队列使用可复用的 SQLite 数字 ID，长期成员记忆却用 `reply:<id>` 和 `activity:<id>` 去重。清理回复后再次使用同一 ID，会撞到长期库的旧事件。检查灯盏堂时，11月6日的三条已确认回复分别撞到了9月29日或10月1日的旧记录，内容和时间均不同。

关系判断原先只看本次整理批次。积极证据先以普通消息整理、已确认回复稍后才进入下一批时，二者无法关联；反过来也可能漏掉。普通消息自身不能证明机器人已实际参与，不能简单取消确认门槛。

## 修复方式

- `memory_delivery.py` 从会话、原消息定位、创建时间、提问、实际回复和发送者生成稳定摘要，区分 `reply-v2`、`activity-v2` 和记忆管理请求。
- 新增 `bot-state.sqlite3.memory_delivery_receipts`，按完整会话/原消息定位确认已经交接，而非仅信任数字回复 ID。已处理前缀不会阻塞后续批次，发件人映射在新请求时更新。
- 旧记忆中只有时间、用户内容和机器人回应一致，才视为已经学习。原始事件已清理时继续核对旧经历记录；不会只按旧 ID 忽略不同的新互动。
- `member_relationships.py` 暂存已通过本人原文和置信度校验的关系候选，最多保留一天，仅保存证据 ID 和文字偏移，不另存私人原话。
- 后续批次只关联同一会话、成员、记忆版本和半小时窗口中的已确认回复/活动。原始证据被删除或版本变化后，候选无法用于加减分。
- 同一窗口已加减分不重复执行。保留积极体验 +1、持续摩擦 −2、和解 +1，以及每日绝对变化最多6分等既有规则。

新增候选只用于关系判断，不混入画像提取和记忆召回的模型输入，不改变资料共享范围。

## 兼容与恢复

首次加载修复后会重新核对仍保留在回复队列里的已确认互动：真正旧记录跳过，之前因撞 ID 遗漏的不同互动正常入队。这个过程不重新发送微信消息、不改写旧事件，也不直接设置好感度。

已经从回复队列清理掉、且没有保留下来的原始互动，不能凭空恢复。过去未保留的模型关系提案不会被编造成历史加分。本次不全量回扫群历史或人工回填分数。

## 验证与发布

回归覆盖 ID 复用、重复交接、活动交接、40条批次后的继续推进、精确旧记录兼容、证据先到/回复先到、窗口和成员隔离、证据删除与版本失效。

另在服务器私有临时目录复制记忆库，验证当前三条撞 ID 的真实回复连续导入两次只新增三条事件，旧事件保留。该验证不改生产库，也不进行真实群发送。

服务器的代码和测试存在既有版本差异，回归需要比较未改动版本与修复版本，明确区分既有失败和新增失败，不能宣称整个测试集全绿。

本次对照：原服务器版本645项，修复版655项；新增10项全部通过，两版相同的8项失败、1项错误无新增。另有本地44项记忆相关测试通过。真实模型隔离验证中，第一批为positive、第二批为neutral，确认回复前不产生关系分数，确认后正确关联前批证据得到51分。

按当前运维要求只部署、不重启机器人。修复在下次正常启动后加载；运行中的旧进程仍使用旧链路。上线前备份源文件，原子替换，检查健康状态和进程身份；回滚代码时不要覆盖当前聊天、记忆和登录数据。
