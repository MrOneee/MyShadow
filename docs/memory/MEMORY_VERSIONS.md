## 2.4.0 有界语义选择

生产Bot将AIClient工厂绑定到MemoryService，评测使用同一生产选择入口。未绑定工厂或配置`member_memory.semantic_read=false`时保留词面路径；有绑定时先按权限取词面候选及最多500条同源事件证据，再构造最多240条、48000字符的目录。词面命中与不同时间的记录交错排列，避免目录预算完全挤掉非词面候选。模型只输出至多12个目录序号，宿主校验并返回实际原话；模型生成的答案不能代替证据。

调用在SQLite事务外进行。删除、纠正、停记与事件到期清理使revision失效，返回前再次检查；发生变化时丢弃旧候选，自动上下文重新读取。调用失败或序号无效时标明词面回退。增加来源删除时的revision触发器，不重提取已有事实/事件。2.3库升级不改写既有记录，模型调用预算变大，但最终6500字符/12条回忆限制不变。

部署须同步member_memory、member_retrieval、member_evidence、新增member_selector和Bot的工厂绑定，保持member_memory_policy及member_profiles为对应版本。可临时关闭semantic_read以回到词面读取，但这不等于整个代码/数据版本回退。正式回退仍采用匹配代码及升级前备份，遵守删除/停记有效性要求。本轮未部署生产。详情见[第二轮方案](memory-2.4-plan.md)。

2.2.0当时为已完成评测的候选版本，尚未部署生产。160题回归中LME正确数25→28、LoCoMo语义59→60，但LoCoMo官方混合分37.77%→35.81%，相同题集token增加21.36%；不能表述为全面优于2.1.0。详细收益、退步和新增题表现以[2.2报告](memory-2.2-evaluation.md)为准。

## 2.3.0 事件原话证据

详见[目标协议](memory-goal-plan.md)与[迭代记录](memory-goal-journal.md)。本版本新增`member_evidence.py`，在记忆提取事务中保存模型筛选的非敏感原话片段。每项必须逐字属于宿主绑定的源事件，带user/assistant角色、event/state/preference/plan/advice类型、来源时间及检索摘要；模型不能指定其他成员或会话。助手片段仅限已确认exchange的advice，不转成用户实际行为。

新增`memory_evidence`与FTS索引，只在原成员、原会话读取，不随共享画像开放。回答时返回校验过的原话，检索摘要不直接作为事实展示。原事件删除时由触发器清理记录和索引；来源90天保留期清理同步生效。指定删除支持只有证据、没有画像的条目；停记阻止读取和写入。已被不可见纠正替换的画像，其对应旧来源证据也受到过滤。每批最多24条，单条原话≤700字符，提取输出上限由6000提高到10000 token；回忆结果仍≤6500字符、最多12条。

2.2→2.3升级只创建空的新表、索引和删除触发器并更新标记，不回扫历史、不自动重新提取、不恢复删除资料。隔离旧库备份验证了既有表内容、事实/经历数量不变，第二次初始化幂等，原库不变；现存原话不会自动进入新索引。需要部署时成套更新member_memory、member_memory_policy、member_retrieval及新增member_evidence，保留当前member_profiles与Bot接线。回退继续采用停服、匹配旧代码及升级前SQLite备份的完整流程，并保留备份后删除/停记操作的效力。未执行生产部署。

## 2.2.0 的行为变化

- 保留一次自动检索与最多两次模型主动回忆的调用预算。检索先过滤可见范围，再使用综合关键词与有界单关键词候选；按相关性、关键词覆盖及来源重复程度选择资料。单次返回最多12条、正文窗口最多600字符，整个读取结果仍限制为6500字符。相比2.1每次最多6条，候选量和可返回条数增加，不能理解为检索计算量完全不变。
- 从命中事实补充同主题的可见历史版本，帮助比较旧值与新值。相同文本如果来自不同事件或时间，不会一律当作重复；同源画像与经历则降低重复权重。一般事实问题优先用用户原话衡量相关性，减少长助手回复的干扰；明确询问助手建议时仍保留建议相关检索。
- 提取阶段从最近200条可见活跃事实中按新事件相关性选择最多12条旧资料，并传入主题与冲突状态；同来源资料才附说出时间。提示明确区分累计数、增量、计划目标、建议和已发生事实，保留原文实体、数值及列表细节。单条100字、每人每批最多6条事实等存储约束仍然存在。
- 普通矛盾陈述不再因为时间较早而自动失效；没有明确更新意图时保留待确认。明确替换或管理纠正按说出时间维护当前版本；相同值的明确确认也保存新版本，用以解除旧冲突。同一时刻的不同值保留待确认，迟到更新补入历史而不覆盖较新状态。未指定新主题的管理纠正沿用原主题。
- `asserted_at`、`valid_to` 与版本指针记录陈述的时间和更替关系，不能直接当成现实事件日期或证明某状态在区间内每一天都成立。已有旧记录不会在升级时被猜测性重判。历史替代指针仍指向当前版本，以继续抑制经隐藏纠正产生的跨范围信息泄漏。
- 读取提示要求核对人物、对象、数值、单位、时间范围和比较方向；多来源问题合并证据后检查缺项，缺失时更换关键词继续回忆，没有依据则说明未知。这是模型提示约束，没有新增确定性的事实验证器，也不保证消除幻觉或算术错误。
- 成员与会话隔离、敏感过滤、同来源引文权限、停记与删除规则保持；普通成员发言不变成已确认的机器人共同经历。没有新增原始聊天全库搜索、向量数据库或外部存储服务。

## 2.1.0 → 2.2.0 的迁移与局限

2.2没有新增数据库表或列。初始化检测到 `meta.memory_version=2.1.0` 时，只在事务中将标记改为 `2.2.0`，不回填原文、不重新提取事实、不重建已有索引、不修改事实状态与历史链，也不恢复删除的记录。再次初始化直接使用已有版本，迁移失败时事务回滚。

隔离验证使用2.1正式评测中的 `6071bd76` 合成用户库，通过SQLite backup API复制后升级。升级前后98条事实、241条经历保持不变；事实全文、证据、状态历史、经历、所有表中除版本标记外的数据以及表结构的SHA-256均相同，第二次初始化相同。原2.1库的逻辑内容、主文件及WAL字节哈希也未改变。该检查没有连接或迁移生产数据库。

旧库直接升级后，已有资料可以使用新的读取与选择规则，后续新消息使用新的提取和状态更新规则；升级本身不会补齐过去遗漏的实体、重建已经压缩掉的信息，或自动清除旧冲突。本轮基准从完整历史写入干净库，包含新提取规则带来的收益，**不能将该分数当作旧库升级后立即获得的分数**。若以后需要旧库重提取，应单独设计保持删除屏障、授权及保留期的迁移，不以删除版本标记触发回填。

另有独立补充诊断：复制52个2.1测试库、仅升级读取逻辑后重新回答原160题。LME正确数25→28、LoCoMo语义59→62，但LoCoMo官方混合分37.77%→36.17%。这组诊断没有重提取，不混入194题主评测；原库内容和版本前后不变。它同样只支持局部收益结论。

## 2.1.0 的行为变化

- `MemoryService.context(..., query='')` 新增可选当前问题；生产 `Bot.messages_for` 在模型/DSH执行前传入问题。每次常规回答自动查一次当前成员资料，随后模型仍最多主动回忆两次。旧版最多两次模型主动回忆；因此本次提升包含更多主动提供资料的预算，并不是完全相同的检索预算。
- compact模式和预算回退不自动检索；旧SocialMemory不接收新参数，仍兼容原接口。已有用户边界与称呼优先，超过6500字符时先丢弃自动检索项；最终仍受Bot的整体上下文预算约束。大量强制边界可能使这一级资料超过6500，6500并非对这些边界的静默截断承诺。
- 保留至多1000字符的用户正文、800字符的确认回复作为经历，而非各取180字符。读取每条经历最多900字符，围绕检索命中选窗口；`truncated`标记窗口不完整，`partial`表示候选未全部返回。单次至多6项、约6500字符的读取预算。
- `fact_evidence_search` 仅索引已经保存且经过校验的事实引文。引文只能按同成员、同来源会话匹配和展示；共享到其他会话的画像仅使用原有事实值索引。没有新增原始聊天全库搜索能力。
- 新提取提示要求“一条事实一个主题”，在明确累计/状态调整时使用同主题替换；不以新时间无条件覆盖旧信息。待确认冲突、失效记录和观察标记仍保留。
- 返回同会话事实的 `asserted_at` 和引文，帮助区分说出时间、记录时间与事件发生时间。没有声称自动推断所有事件日期。
- 删除事实自动清理辅助索引；部分删除同时清理引用同一来源的其他类别事实的引文及索引，保留无关事实本身。

## 旧基线 → 2.1.0 的数据兼容与迁移

原有主表、账号/成员/会话标识、权限规则、用户管理命令和保留期不变。新增一个FTS5辅助表、一个删除触发器和一个meta版本值；没有改变事实/经历表列结构。

首次构造MemoryService时，在同一数据库事务中：

1. 创建辅助索引和删除触发器。
2. 对现存事实的现存引文重建索引。
3. 仅对仍然存在、源事件仍保留且已处理、成员未停记的经历补全正文；不新增经历，不从微信原始数据库回扫，不恢复已经删除的记录。
4. 写入2.1.0版本标记。再次启动不重复回填。

若原始事件已经到90天保留期限而被删除，旧经历的缺失尾部无法恢复；已删除的引文也不会被重建。首次升级需要遍历现存事实与可恢复经历，耗时随数据量增长；普通后续启动不会重复此扫描。迁移失败则事务回滚，不留下部分版本标记。

## 部署与回退步骤

离线迭代阶段未执行生产部署；用户随后明确授权，2.10已于2026-10-23部署，详情见[生产部署记录](memory-2.10-production-deployment-2026-10-23.md)。以下为通用流程，必须先识别实际线上代码与数据库版本。

建议部署时按以下顺序操作：

1. 停止机器人及其记忆后台线程，保持生产数据库不再写入。
2. 用SQLite backup API或等价的完整备份方法备份数据库。WAL模式下不能只复制主 `.sqlite3` 文件而忽略尚未检查点的WAL内容。保留与备份对应的旧代码版本和配置。
3. 部署2.10时核对该轮 `manifest.json` 中10个生产源文件的哈希和完整依赖，成套整合记忆服务、策略、检索、证据、选择器、日历与Bot接线；不能只替换版本常量或单个提示文件。评测快照不是完整应用发布包，保留工作区其他独立功能修改与当前运行环境。
4. 启动机器人，检查 `SELECT value FROM meta WHERE key='memory_version'` 为 `2.10.0`，并用隔离用户验证回忆、明确纠正、停记、部分删除和全部删除。2.9→2.10只更新版本标记，核对除该标记外所有表内容不变、重复初始化幂等；更早版本须同时阅读对应迁移说明。
5. 需要回退时先停服务，成套恢复升级前的代码和SQLite备份，再启动；明确处理备份后新增数据，不能无声丢弃。不要在仍写入的迁移后数据库上交替运行两个版本。

旧代码通常能忽略新增表，但它不会维护新增引文索引，也不知道新的版本标记。因此“仅换回旧代码继续写库，再切新代码”不属于支持的回退流程。不要只删除版本标记反复回填来代替备份恢复。

尤其不能把2.1代码直接指向标记为2.2的库：2.1不能识别2.2标记，会进入其旧版回填分支，可能重建经历或索引，并继续按旧的冲突规则写入。2.2回退到2.1也必须使用匹配的升级前备份；回退前核对备份后产生的新消息、纠正、停记和删除操作，避免恢复被用户删除的资料。若不能保持这些操作的效力，应先停止迁移并另行处理数据，不能把代码回退视为数据自动兼容。
